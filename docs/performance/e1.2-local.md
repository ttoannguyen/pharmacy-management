# E1.2 local verification

Status: complete for the catalog lifecycle scope on 2026-08-18.

## Delivered contract

- Store products can be updated and soft-archived through application services
  and `PATCH`/`DELETE /api/catalog/products/:id`.
- Mutations require a reason and `expectedUpdatedAt`, enforce tenant ownership,
  permissions and state, and write safe audit before/after values.
- Store edits never mutate a linked shared catalog record; explicit local
  overrides are retained.
- SKU conversion changes create immutable `StoreSkuConversionVersion` rows.
  Price-only changes do not create a conversion version.
- Archived product, SKU and historical transaction references are retained.

## PostgreSQL evidence

- All six committed migrations applied from an empty PostgreSQL database.
- The new migration backfilled an existing SKU to conversion version 1 in a
  populated-upgrade check.
- Seed was run twice and remained idempotent: one SKU and one version-1 row.
- The synthetic fixture created 1,000 products, 5,000 SKUs, 5,000 barcodes and
  5,000 conversion versions, then removed all fixture rows.
- Database guards rejected a second current version (`23505`), non-positive
  quantity (`23514`) and cross-tenant reference (`23503`).

## Browser evidence

Both Chromium and Firefox passed all 16 criteria. Product update/archive and SKU
add/update/archive each produced exactly one mutation request and one bounded
detail GET, with no catalog-list or overview waterfall. The SKU conversion moved
from version 1 to version 2, and archived test records were not left active.

## Boundary for the next phase

E3/E5 must add document-state archive guards and preserve conversion/cost
snapshots on transaction lines. Deployed same-region load/provider telemetry and
unrecoverable historical baselines remain explicit performance-plan exceptions;
this local report does not claim they are complete.
